## wal-recycled/
Options as wal-basic plus `recycle_log_file_num=2` (=> EVERY WAL record uses recyclable types 5..8 with 11-byte headers carrying the log number). Rounds below. r2 is large (~28 KiB), the others small. Each flush obsoletes the previous WAL and queues it for recycling; the next new WAL is created by renaming a queued file (engine LOG: `reusing log N from recycle list`). The WAL that holds r4 is the renamed r2 file, so it keeps r2's longer content behind r4's records. Because r4's records are not the same size as r2's, the first byte after r4's last record lands in the middle of an older record (undecodable); intact older records (header log number = the previous owner of the file) resume further on. See scan for exact offsets.

**The directory is a snapshot copied while the DB was still open** (equivalent to a crash/power-loss image): a clean close truncates the live WAL to the bytes written and would remove the stale tail. CURRENT/MANIFEST/OPTIONS are consistent with it; r4 is unflushed so only the WAL holds r4 (WAL replay on open would be needed to see it; RocksVision never replays).
